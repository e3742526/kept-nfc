# Kept native capture integration contract

Contract version **3** · 2026-11-23

This contract applies to the bundled iPhone app using the existing Kept server, session, uploads and sync ledger. The ordinary browser queue continues to send payload version 1.

## Session and capability

- New iPhone sessions require native **Sign in with Apple**. Generate independent 32-byte random PKCE verifier and callback state values, encoded as unpadded base64url. Set the Apple request nonce to the unpadded base64url SHA-256 of `kept-native-apple-v1\n<canonical origin>\n<PKCE-S256 challenge>`, with literal line feeds between fields.
- Send `POST /api/v1/native/apple` with the exact Kept `Origin` header and no cookie. The JSON body is `{"identityToken":"<Apple JWT>","verifier":"<PKCE verifier>","state":"<callback state>"}`. Kept checks the Apple signature, issuer, iPhone bundle audience, age, expiry and nonce, then consumes the nonce and returns HTTP 200 `{"appleToken":"<opaque continuation>"}` with `Cache-Control: no-store`. Start a new Apple authorization after an expired or consumed proof. A server missing this route requires an upgrade for new iPhone sign-ins.
- Open `GET /native/connect?appleToken=<opaque continuation>` in the system browser authentication window. The continuation is valid for ten minutes on the same server and restore epoch. A linked Apple subject selects its existing Kept account. Finish Kept MFA when enabled. First-time linking requires a fresh browser sign-in to the existing Kept account and explicit approval showing both email addresses. Apple relay addresses are supported. A matching email never links accounts automatically. Browser sign-in methods remain available for ordinary browser use and first-time linking.
- Consent `POST /native/connect` sends the same `appleToken` as a form field, plus `confirmLink=yes` when explicitly linking. The one-time approval redirects with HTTP 303 to `kept-nfc://auth/callback?code=<code>&state=<state>`. Validate callback and state, then exchange the code within two minutes with `POST /api/v1/native/exchange` and JSON `{"code":"…","verifier":"…"}`. HTTP 200 sets a first-party session cookie and returns `{"account":"<user UUID>","epoch":"<restore UUID>"}`. The app stores the session in Keychain. Existing Kept iPhone sessions remain valid under their normal expiry and revocation rules.
- Fix the server origin to the selected connection. Use its session cookie and send `X-Kept-Native-Account: <account>` and `X-Kept-Native-Epoch: <epoch>` on native API requests. The account value identifies the signed-in user. The epoch identifies the current database generation.
- The capture-capability response keeps its own `contractVersion: 1`. Before **each** replay attempt, including manual retry after being offline, send `GET /api/v1/native/capture-capabilities` with that session and both headers. HTTP 200, `Cache-Control: no-store` body:

  ```json
  {"contractVersion":1,"capturePayloadVersions":[2,3,4],"account":"<user UUID>","epoch":"<restore UUID>"}
  ```

  Verify the capability response version, that the supported list contains the operation’s required version, and that both context fields match. Check on the configured origin before the first upload or capture mutation. Keep the result for that attempt only. Treat missing route (404), non-contract response (including an HTML fallback), or missing supported version as recoverable server incompatibility. Retain the queued record, its request key and original files and retry negotiation when service returns or the server is upgraded. An already authenticated phone still negotiates.

  A pre-negotiation native server may answer 401 on the missing route because its context hook runs before the 404. On capability 401, check `GET /api/v1/me` with the same session and context before prompting for sign-in. An authenticated 200 on `/me` means recoverable incompatibility. A 401 there requires re-authentication. A network error, rate limit or server failure remains retryable.

## Replay and confirmation

- Upload with `PUT /api/v1/files/:fileId` using the existing upload query and headers, including native context and `X-Kept-Sha256`. On HTTP 200/201 use the returned canonical `id` and verify `sha256` and `bytes`; on deduplication the returned ID can differ from the requested ID. Keep upload identities stable across retries.
- Send `POST /api/v1/sync/ops` with the existing `{clientVersion, ops:[…]}` envelope. New named entries with an explicit observation or addition use `op: "create_thing"`, `payloadVersion: 3`, `captureIntent: "record" | "add"`, `target: {containerId}` or `target: {placeId}`, `reviewSuggestions: true`, and file roles `photo` or `document`. Keep the thing ID, client ID, operation key, timestamp and payload stable across retries. Stored native drafts without capture intent still use version 2. A v1 draft made by the earlier native client can send its original body and identifiers as v2. The server recognizes exact legacy-v1 ledger replays under the original key. Existing terminal outcomes retain their meaning.
- Captures saved with ChatGPT or Apple Intelligence use the same fields plus `skipServerSuggestions: true` and require `payloadVersion: 4`. The server saves the photo and reviewed description and skips its extraction job. Older servers hold these captures in the phone's outbox until version 4 becomes available.
- A photo observation still negotiates capability before uploads. It uses the existing `create_thing` operation with `payloadVersion: 1`, `mode: "thing"`, `attachToThingId`, `target: {unplaced: true}` and `photo` files. The draft UUID identifies this observation and the sync result points to the existing thing. The server appends photos without editing fields or containment.
- Versions 2 and 3 require native context. Kept continues serving ordinary v1 operations and v1 snapshots. A server that lacks the requested version rejects the envelope with HTTP 409 `server_outdated` before writing an operation result. This also protects the ledger if the server changes after negotiation.
- Completion requires the matching sync result (`results[]` entry with the original `clientId` and `idempotencyKey`, `outcome: "applied"`, and `entity: {type: "thing", id: "<record UUID>", shortCode?: string | null}`). The expected entity is the new record for a named capture and `attachToThingId` for an observation. Confirm every original against the paginated `items` from `GET /api/v1/things/:id/attachments?limit=100` by attachment role, file `sha256` and `bytes`. A replayed result counts once when the phone durably completes its local entry. Until then retain the local queue entry and originals. Authorized original access uses `POST /api/v1/files/:id/url` and the returned short-lived download URL.

## Bin actions

- The unchanged check uses `POST /api/v1/things/:id/box-check` with `unchanged: true` and the full set of direct inventory lines, with identical expected and found quantities. A stale set is rejected. A successful check confirms the listed records and leaves nested contents’ direct sightings alone.
- Location edits use `POST /api/v1/things/move`. A physical move can include a partial quantity. `intent: "correct"` changes recorded placement within the same location without a fresh sighting. `intent: "remove"` moves the record to that location’s Unplaced area and marks it uncertain. Both require the current row version and server support for version 3. The audit records the prior path and supports undo.
- Native label sheets use the existing blank label batch and claim routes. The 8, 12 and 24 label US Letter stocks have writable space and use the same stable short IDs as scanning. Reprint reads the saved batch and preserves every encoded identity.

## Failure and recovery

Errors use Kept's `{error, code, hint?, …}` body. Network failure, HTTP 429, 5xx, a missing sync result, or unavailable attachment confirmation are retryable with the same identity. HTTP 401 or MFA-related refusal requires authentication for the same origin and user. HTTP 409 `server_outdated` or `client_outdated` blocks replay pending a compatible server or client respectively. After `target_missing` or `target_trashed`, an explicit retarget of a new entry retains the record and local files and uses a new operation key. An observation stays bound to the original item and its originals stay available for review. Permission refusal, invalid payload, checksum mismatch or idempotency mismatch requires review of that capture.

Restore mismatch is HTTP 409 `{"code":"conflict","error":"…","reason":"restore_epoch_mismatch","hint":"…"}`. An authenticated exchange returning a different epoch for the same origin/account also identifies a restore or replacement. Hold pre-restore entries and originals under their original scope. Ordinary pending replay requires the same origin, account and epoch. Same-origin, same-owner held entries can be reviewed or exported after re-login. Keep held entries inaccessible to other accounts and origins. Automatic replay or reconciliation of held work is outside this contract.

## Reviewed photo entries

- The optional `POST /api/v1/native/photo-proposals` accepts `{locationId,jpeg}` with the usual session, origin and native context. The JPEG is a bounded inference copy. Server API preview uses the location’s extraction provider, ROOM prompt and object validation. It creates no inventory, file, or extraction job. The response has up to 12 proposed items with names and optional quantities and categories.
- Apple Intelligence and ChatGPT plan suggestions validate to the same proposal shape on the phone. The selected provider receives the inference copy only when requested. The device retains the original separately.
- Opening a photo review stores the original and a review manifest in the origin, account and restore context. The manifest holds entries, inclusion, edits, categories and destination. An unapproved manifest never enters automatic replay.
- Approval records the device save time and locks the selected entry identities. The phone uploads the original once per replay attempt under its stable file ID, verifies the checksum and size, and puts the canonical file ID on every accepted payload v4. Shared photo references use the ordinary authorized attachment and file lifecycle. ROOM completion and its source-photo retention setting do not apply.
- Each entry uses its own stable client ID and operation key, with the same batch ID. Requested category assignments use the existing batch-tags endpoint with a separate stable key. A successful sync result, matching original attachment, and category write are required for each entry. The manifest records entries verified so far and completes when all approved entries are verified.
- This adds no sync payload version or migration. The standard version 4 hold covers servers that cannot replay a reviewed photo. A server without the optional preview route can still sync approved local-provider reviews when it supports version 4.

### Reviewed photo batches

The native preview has an optional `description` alongside the name, quantity estimate and category suggestions. NativeStore holds the proposal edits and supporting photo indexes until review is approved. Replay uses existing capture payload v4 for the approved new records and the ordinary attachment capture for supporting evidence on the destination bin or other existing records. The existing category write and row-versioned record PATCH complete the user-selected updates. All these writes have stable replay IDs. Older servers that lack the required capture version hold the durable review before upload. The review and photo-only operations share a batch ID, and the original files use the existing scoped attachment, export and restore paths.
